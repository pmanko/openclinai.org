Washington Health Summary (WAHS) · Architecture & Empirical Strategy

How WAHS connects open-weight AI to patient health records safely and fast.

When a patient asks a question about their health history in Washington Health Summary (Woz/WAHS), how should the system give the AI the right medical context without exposing other patients' records, running out of memory on large charts, or making the user wait? This page summarizes the three approaches evaluated by the UW CIRG & WAHS team, shows what our live benchmarks across 9 open-weight models already prove, and outlines the pilot architecture.

Section 1 · Three Strategies Under Consideration

Condense first, retrieve what doesn’t fit, and keep the AI inside one patient’s boundary

Raw FHIR health records are notoriously verbose: a single multi-year synthetic patient chart reaches 18–19 MB (~1.35 million tokens of raw JSON), and real longitudinal patient exports can reach 100–200 MB with hundreds of free-text clinical notes. Rather than treating chart condensation, retrieval (RAG), and semantic search as mutually exclusive, they form a staged pipeline.

Approach 1 · Pilot Target (Implemented)

Condense into Context + Targeted Overflow Recovery

The WAHS engine fetches the logged-in patient’s authorized FHIR bundle once, shrinks it by 90%–99% into a clean clinical ledger with [N] source links, attaches automated clinical conflict checks, and pulls in any older notes or labs matching the user’s question.

  • Immediate streaming: Everything happens in ~100 ms before a single AI call, so answers stream right away.
  • No missed codes: Deterministic clinical rules map terms like “diabetes tests” to HbA1c, glucose, and kidney labs without relying on a small AI model to guess LOINC codes.
  • Strict patient boundary: The AI never queries a shared database directly; it only sees the single patient’s pre-scoped bundle.
Approach 2 · Hybrid Extension (For 100–200 MB Charts)

Semantic Search Over Long Clinical Notes

Free-text clinical notes (such as 4,000- to 14,000-word palliative care, oncology, or hospital discharge notes) carry the richest context in a chart but cannot all fit verbatim in an 8k summary.

  • Combines with Approach 1: Keep the structured 8k condensed summary (allergies, active meds, problems, recent labs) in context, and index the patient’s long free-text notes in memory.
  • Question-targeted excerpts: When a question asks about a past hospitalization or specialist note, retrieve the top matching note paragraphs with their [N] source citations.
  • Single-patient scope: Embeddings are computed or cached strictly within the authenticated patient’s record.
Approach 3 · Future Multi-Agent Stage

Live Agentic FHIR Querying (MCP / Tool Calls)

An AI agent translates the user’s question into clinical terminology (LOINC, SNOMED CT, RxNorm), queries a live FHIR server for matching resources, condenses the returned FHIR JSON, and answers.

  • Why defer past the pilot: Smaller open-weight models frequently miss relevant LOINC codes when writing raw FHIR queries, and raw FHIR responses still have to be condensed before the model can read them.
  • Security & audit bar: Pooled records often link multiple clinic IDs under one master patient ID; letting an AI generate live FHIR queries requires strict query-scoping guardrails first.
  • Multi-step latency: Requires an orchestrator + retrieval team with visible UI progress steps.
Why combining Approach 1 + Approach 2 gives the best pilot foundation: Even when an AI retrieves records via RAG, raw FHIR JSON is too bulky to hand directly to the model. Having the WAHS engine condense what fits into the core summary and pull question-relevant clinical notes from the same patient’s pre-scoped bundle delivers RAG’s scalability without exposing the FHIR server to model-generated queries.

Section 2 · Architecture Questions vs. Empirical Evidence

What our live evaluations already answer

Every major technical question raised in our architecture review has been tested against synthetic multi-clinic records (up to 18.8 MB) and real de-identified hospital/ICU records from PhysioNet MIMIC-IV-FHIR (up to 251,000 clinical tokens). The table below links each question to our plain-English findings and source code.

Architecture Question What Our Live Benchmarks & Code Show Live Report & Code Links
1. Can lossless & grouped FHIR condensation shrink records by ~90% without losing clinical facts? Yes — 90% to 99.4% token reduction with 100% safety-core retention. Our deterministic condenser strips FHIR syntax boilerplate, deduplicates repeated lab panels into compact timelines, and prioritizes the HL7 International Patient Summary (IPS) safety core (allergies, active medications, active problems, implants). On an 18.8 MB chart, lossless structural condensation cuts tokens by >90%, and grouped clinical condensation fits the core chart into 8,000 tokens (99.4% reduction) while recording every omitted item in a completeness manifest. Section 4 · Pilot System Architecture

How Woz, the WAHS Engine, and the UW GPU server fit together

Following the team’s architecture review, the WAHS pilot separates responsibilities across three clean layers so the FHIR store stays standard, the Woz frontend stays simple, and the GPU server only runs model inference.

[1. Woz Frontend & Auth Proxy] • Patient logs in; Woz auth proxy enforces patient-scoped FHIR access (master patient ID) • Simple Chat Tab sends OpenAI-format request (conversation history + patient context) │ ▼ (OpenAI REST /v1/chat/completions, stream=true) [2. WAHS Engine (Scoped from Med Agent Hub · Separate Server)] • Condenses the patient's authorized FHIR bundle by 90%–99% (condenser.py) • Runs deterministic 4-Layer Clinical KB + Patient Relationship Graph (clinical_graph.py) • Pulls omitted clinical notes / labs matching the user's question (wahs_tools.py) • Keeps [System Prompt + 8k Condensed Chart] as a fixed prefix for GPU session caching │ ▼ (OpenAI REST /v1/chat/completions + KV prefix cache reuse) [3. UW CIRG GPU Server (Gemma 4 12B / 26B / E4B)] • Streams tokens back immediately (single-call workflow; < 0.3s follow-up prefill with cache) • Engine attaches [N] → FHIR resource UUID & date mappings for clickable source inspection
Security & Access Control

Enforcing the single-patient boundary before any AI call

  • Scoped at login: Existing authentication proxies in Woz enforce OAuth scopes and resolve a patient’s pooled records (across clinics that may use different local medical record numbers under one master patient ID) before the WAHS Engine processes the bundle.
  • No cross-patient query surface: In the pilot, the AI model never writes database queries against a multi-patient FHIR server; all condensation, clinical rule checks, and note lookups run strictly inside the logged-in patient’s isolated bundle.
  • Screen-sharing & sensitive history controls: Patients can toggle 42 CFR Part 2 / WA My Health My Data Act segmentation, and the engine automatically withholds sensitive social/survey entries when a caregiver or bystander is viewing the screen.
Multi-Turn Memory & Fast Streaming UX

Instant follow-up answers via GPU prefix caching

  • Multi-turn from day one: The Woz chat interface passes the conversation history with each turn so patients can ask natural follow-up questions.
  • Prefix-cached chart memory: By placing the static [1]...[N] condensed patient chart at the very top of the prompt and appending turn-specific rule alerts and chat turns below it, the GPU server reuses its cached memory (KV cache) across follow-up questions for the same patient.
  • Transparent progress cues: Single-call streaming starts almost immediately for the pilot; as multi-step retrieval or specialist checks are added later, lightweight status steps (“Checking medication conflicts…”, “Reading discharge note…”) keep the user informed.
