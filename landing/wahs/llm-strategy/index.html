Washington Health Summary (WAHS) · Architecture & Empirical Strategy

How WAHS connects open-weight AI to patient health records safely and fast.

When a patient asks a question about their health history in Washington Health Summary (WAHS), how should the system give the AI the right medical context without exposing other patients' records, running out of memory on large charts, or making the user wait? This page summarizes the three approaches evaluated by the UW CIRG & WAHS team, shows what our live benchmarks across 9 open-weight models already prove, and outlines the pilot architecture.

Section 1 · Three Architectural Approaches Under Comparison

Condense into context, retrieve long notes via semantic search, or dynamically query FHIR

Raw FHIR health records are notoriously verbose: a single multi-year synthetic patient chart reaches 18–19 MB (~1.35 million tokens of raw JSON), and real longitudinal patient exports can reach 100–200 MB with hundreds of free-text clinical notes. The WAHS team is comparing three architectural options—selecting Full-Chart Condensation as the first pilot iteration while running head-to-head evaluations against dynamic FHIR querying and semantic search over long notes.

Option 1 · First Pilot Iteration

Condense FHIR Record into Context

The WAHS engine reads the logged-in patient’s current FHIR data from the HAPI FHIR server that runs as part of the WAHS deployment, shrinks it by 90%–99% into a clean clinical ledger with [N] source links, attaches automated clinical conflict checks, and sends it with the prompt in a single AI call. Because WAHS is a personal health record, this data changes over time: patients download records from their providers’ EHRs (for example via USCDI or TEFCA), enter their own concerns and goals through web forms, and curate what they keep. The condensed ledger must reflect the record as it stands when the question is asked, not a one-time snapshot.

  • Immediate streaming: Everything happens in ~100 ms inside the engine before a single AI call, so answers stream right away.
  • No missed LOINC codes: Deterministic clinical rules map terms like “diabetes tests” to HbA1c, glucose, and kidney labs without requiring a small AI model to write raw FHIR queries.
  • Strict patient boundary: The AI only ever sees the single patient’s pre-scoped bundle.
Option 2 · Unstructured Data & 100–200 MB Charts

Embeddings & RAG for Long Clinical Notes

Free-text clinical notes (such as 4,000- to 14,000-token palliative care, oncology, or hospital discharge notes) carry the most valuable context in a chart, and real patient exports can reach 100–200 MB.

  • Combines with Option 1: Condense the structured core chart (allergies, active meds, problems, recent labs) into context, and use embeddings / RAG for the long unstructured notes that do not fit.
  • Question-targeted excerpts: When a question asks about a past hospitalization or specialist note, retrieve the top matching note sections with their [N] source citations.
  • Single-patient scope: Embeddings and retrieval remain strictly scoped to the authenticated patient’s record.
Option 3 · Under Active Evaluation

Dynamic Agentic FHIR Querying (MCP / API)

For a question like “Have I had any labs for my diabetes?”, the model identifies relevant clinical concepts, translates them into LOINC / SNOMED codes, queries the FHIR endpoint for those observations, and condenses the returned FHIR response.

  • Terminology challenge for smaller models: Larger frontier models know LOINC/FHIR syntax natively, whereas smaller open-weight models often need an injected knowledge base or a specialist retrieval agent to translate clinical questions into codes accurately.
  • Retrieved FHIR still needs condensation: Raw FHIR query responses remain token-heavy and benefit from engine-side condensation before synthesis.
  • Security & multi-agent UX: Requires strict query guardrails across pooled multi-clinic patient IDs, plus UI progress steps for multi-agent orchestration + retrieval.
How the approaches fit together: These three options are complementary rather than mutually exclusive. Even when records are retrieved dynamically via FHIR queries or semantic search, raw FHIR JSON is costly in tokens and needs condensation. Starting the pilot with Option 1 (Condense what fits into context) while benchmarking Option 2 (Note embeddings) and Option 3 (Dynamic FHIR querying) on smaller models gives WAHS a fast pilot today and a clear path for 100–200 MB records.

Section 2 · Architecture Questions vs. Empirical Evidence

What our live evaluations already answer

Every major technical question raised in our architecture review has been tested against synthetic multi-clinic records (up to 18.8 MB) and real de-identified hospital/ICU records from PhysioNet MIMIC-IV-FHIR (up to 251,000 clinical tokens). 1. Can lossless & grouped FHIR condensation shrink records by ~90% without losing clinical facts? Yes — 90% to 99.4% token reduction with 100% safety-core retention. Our deterministic condenser strips FHIR syntax boilerplate, deduplicates repeated lab panels into compact timelines, and prioritizes the HL7 International Patient Summary (IPS) safety core (allergies, active medications, active problems, implants). On an 18.8 MB chart, lossless structural condensation cuts tokens by >90%, and grouped clinical condensation fits the core chart into 8,000 tokens (99.4% reduction) while recording every omitted item in a completeness manifest. Section 4 · Pilot System Architecture

How the WAHS Frontend, the WAHS Engine, and the UW GPU server fit together

Following the team’s architecture review, the WAHS pilot separates responsibilities across three clean layers so the FHIR store stays standard, the WAHS frontend stays simple, and the GPU server only runs model inference.

[1. WAHS Frontend & Auth Proxy] • Patient logs in; WAHS auth proxy enforces patient-scoped FHIR access (master patient ID) • Simple Chat Tab sends OpenAI-format request (conversation history + patient context) │ ▼ (OpenAI REST /v1/chat/completions, stream=true) [2. WAHS Engine (Scoped from Med Agent Hub · Separate Server)] • Reads the patient's current records from the WAHS HAPI FHIR server and condenses them by 90%–99% (condenser.py) • Runs deterministic 4-Layer Clinical KB + Patient Relationship Graph (clinical_graph.py) • Pulls omitted clinical notes / labs matching the user's question (wahs_tools.py) • Keeps [System Prompt + 8k Condensed Chart] as a fixed prefix for GPU session caching │ ▼ (OpenAI REST /v1/chat/completions + KV prefix cache reuse) [3. UW CIRG GPU Server (Gemma 4 12B / 26B / E4B)] • Streams tokens back immediately (single-call workflow; < 0.3s follow-up prefill with cache) • Engine attaches [N] → FHIR resource UUID & date mappings for clickable source inspection
Security & Access Control

Enforcing the single-patient boundary before any AI call

  • Scoped at login: Existing authentication proxies in WAHS enforce OAuth scopes and resolve a patient’s pooled records (across clinics that may use different local medical record numbers under one master patient ID) before the WAHS Engine processes the bundle.
  • No cross-patient query surface: In the pilot, the AI model never writes database queries against a multi-patient FHIR server; all condensation, clinical rule checks, and note lookups run strictly inside the logged-in patient’s isolated bundle.
  • Patient-controlled sharing: Patients choose which of their records to share by creating an International Patient Summary (IPS) within WAHS and sharing it via a SMART Health Link.
Multi-Turn Memory & Fast Streaming UX

Instant follow-up answers via GPU prefix caching

  • Multi-turn from day one: The WAHS chat interface passes the conversation history with each turn so patients can ask natural follow-up questions.
  • Prefix-cached chart memory: By placing the static [1]...[N] condensed patient chart at the very top of the prompt and appending turn-specific rule alerts and chat turns below it, the GPU server reuses its cached memory (KV cache) across follow-up questions for the same patient. When the patient’s records change, the condensed chart is rebuilt so answers reflect the current record.
  • Transparent progress cues: Single-call streaming starts almost immediately for the pilot; as multi-step retrieval or specialist checks are added later, lightweight status steps (“Checking medication conflicts…”, “Reading discharge note…”) keep the user informed.
