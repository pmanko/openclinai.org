Washington Health Summary (WAHS) · AI strategy

WAHS AI architecture and model strategy.

When a patient asks about their health record, the AI needs the right parts of that record. It must never see another patient’s data, large records still have to fit, and the answer should not take long. This page explains the approach the UW CIRG & WAHS team chose and the evidence behind it.

Updated November 2026 · Written for the whole project team · Developers: Engine reference →

Key decisions

  1. Condense only when a record exceeds the available context budget. Continuous verbatim-first preprocessing keeps the full extracted record and clinical notes intact whenever they fit the model’s dynamic per-turn capacity (or an explicit test budget), applying uniform series folding and safety-core packing only when constrained.
  2. A lean, domain-neutral middle service does that work. The WAHS engine sits between the WAHS app and the model server with zero database and zero hardcoded clinical heuristics or ad-hoc privacy rules, while optional research modules (note passage search, overflow lookup, longitudinal trends, and clinical reconciliation) sit behind a clean extension interface disabled by default.
  3. Open-weight model tiers backed by H200 benchmarks. Pilot deployments default to wahs-26b (Gemma 4 26B, with wahs-12b and wahs-e4b selectable). In our November 900-cell H200 benchmarks (evaluated at a fixed 16k calibration setting), Gemma 4 26B led at 85.1 / 100 with 0 of 75 confirmed unsafe answers (3.4 s median wait), while Gemma 4 12B reached 82.0 to 82.8 / 100 on tighter GPU VRAM budgets.

System components

Three components with separate responsibilities

A question passes through three components. Each can change without touching the other two.

  1. CIRG · patient-facing app

    WAHS app

    • Shows the chat and the record.
    • Keeps the conversation in the browser.
    • Sends each question through its own server, never straight to the model.
  2. →↓ question and sign-in

  3. This project · middle service

    WAHS engine

    • Fetches the signed-in patient’s current record via the fhir-auth proxy.
    • Runs continuous 3-tier verbatim-first FHIR R4 condensation.
    • Supports optional modular research extensions (disabled in baseline).
    • Returns the answer with clickable [N] source provenance.

    Reads from the record store using the patient’s own sign-in. The engine has no access of its own, so it can only ever receive that patient’s records.

  4. →↓ condensed chart and question

  5. UW CIRG GPU server · or an agency’s own

    Model server

    • Runs the open-weight model: Gemma 4 26B by default (or 12B / E4B).
    • Keeps nothing between requests.
    • Can be any server that speaks the standard OpenAI chat format.
The app does not call the model directly, for three reasons. The model server cannot check who is asking. A raw record is too large: on big charts the start of the record was cut off and answers scored 0 to 2.8 out of 100. And the answer would carry no links back to source records.

Worked example

Tracing “What are my diabetes labs?” through four steps

Record checking and condensation run inside the engine in about a tenth of a second. Almost all of the wait is the language model streaming its answer. Optional research modules (such as BM25 note search or clinical guideline rules) attach modularly during comparative benchmarks without complicating this baseline path.

  1. The app sends the question and sign-in token.

    It sends the conversation so far alongside the patient’s sign-in token. The browser never uploads raw record bundles or opens a direct connection to the GPU server.

  2. The engine verifies freshness and retrieves scoped records. Checked every turn

    It queries the FHIR authorization proxy using the caller’s own token and checks record modification stamps. Unchanged datasets reuse in-memory cache; newly imported or edited clinic records re-fetch automatically.

  3. The engine runs continuous verbatim-first condensation. Query-invariant prefix

    Transport boilerplate and duplicate clinical note copies are stripped cleanly. When the chart fits the turn’s context budget, every item and decoded note stays verbatim; when constrained, repeated historical series fold uniformly while preserving the HL7 IPS safety core, numbering entries [1]…[N] and reporting any omissions in a completeness manifest.

  4. The model streams a citation-grounded reply.

    Because the condensed chart sits first and stays identical across follow-up turns, the model server reuses its cached prefix and responds quickly. Each clinical claim carries [N] badges linked to the exact source FHIR record, and undocumented requests trigger an explicit abstention.

Approaches compared

Condensation is the pilot default; note search and model queries build on it

A raw health record is far too large to hand to a small model. One multi-year test record is 18.4 MB, and real exports can reach 100 to 200 MB. The team compared three ways to give the model what it needs. They are not rivals: the second and third still need condensation.

Evaluated benchmark · 26B @ 16k

1. Condensation + Clinical Rule Extensions

Method
Condense the FHIR R4 chart into a numbered summary, optionally attach clinical guidelines and entity links via the extension interface, and answer in one call.
Strengths
Highest evaluated safety and speed: single stateless model call with strict per-patient scoping.
Architecture mapping
Standalone baseline serves pure verbatim-first condensation (wahs-26b default), while clinical reconciliation and guideline modules stay isolated as opt-in research extensions.
900-cell H200 result
85.1 / 100 on Gemma 4 26B (0 of 75 unsafe, 3.4 s median); 82.0 on 12B.
Deep-note extension

2. Condensation + Note passage search

Method
Pair the condensed chart with question-matched Okapi BM25 passages from long clinical notes when enabled as an operator-configured extension.
Strengths
Strongest pure clinical note recall on hospital and specialist narratives of 4,000 to 14,000 tokens.
Limitations
Slightly larger turn suffix, adding ~1.5 s to median answer time.
900-cell H200 result
83.4 / 100 on Gemma 4 26B (8.94/10 clinical accuracy); 82.8 on 12B (0 of 75 unsafe).
Evaluated · higher risk

3. Agentic tool-calling

Method
Give the model a compact 2k summary and let it invoke multi-step search tools over the full record before answering.
Strengths
Can inspect deeply buried historical items when a large model chooses effective search terms.
Limitations
Iterative searches frequently miss cross-clinic hold notes or clinical context across fragmented entries.
900-cell H200 result
65.8 to 69.4 / 100, concentrating 24 of 37 confirmed unsafe answers and 93% of over-refusals.

Test evidence

Five findings that support the design

Tested on 18 record bundles from 10 patients, including synthetic multi-clinic records and real de-identified hospital records.

Condensing removes 90 to 99% of a record and keeps the safety core

Condensing removed 90 to 99.4% of the size and kept the full safety core: allergies, active medications, active problems and implants. An 18.4 MB record fits in 8,000 tokens, and every omitted item is counted.

Condensation report ↗

The engine looks up omitted items before calling the model

This covers the case where the answer sits in a part of the record that was left out. On very small summaries, the lookup raised Gemma 4 12B from 47.0 to 68.2 out of 100, with no unsafe answers.

Overflow lookup report ↗

Added clinical knowledge helps models of 4B and larger

Small models do not know lab codes or drug interactions. Adding clinical rules improved accuracy. Adding the patient’s own links between conditions, medications and labs cut unsafe answers by 43 to 71%.

Nine-model report ↗

An overfull model silently drops the start of the chart

This is why the engine condenses the record instead of sending a very large chart. On a shared GPU with a 16k limit, sending 32k to 128k of chart text erased allergies and medications, and scores fell to 0 to 2.8 out of 100.

Chart size report ↗

Citation rules limit guessing by the model

Every claim must cite a source record, and the model must say when the record has no answer. In tests built to pressure it into guessing, Gemma 4 12B gave 2 unsafe answers in 36 and no made-up citations.

Nine-model report ↗

Design clarifications

Nine points on sessions, data handling and deployment

These points were raised in project meetings. Full detail is in the Engine reference.

The chat session is kept in the patient’s browser

On each turn the app sends the conversation so far. Neither the engine nor the model server keeps a copy, and there is no session ID. Starting a new chat clears the browser’s copy.

Sessions and scope →

No new database holds patient data

The engine holds the condensed chart in memory to save time, tied to the signed-in patient, and loses it on restart. Before real records are used, prompt logging on the model server is turned off.

The KV cache is a speed feature and cannot cross patients

The KV cache is the model’s short-term memory of text it has just read. It is not the knowledge base (KB). The model skips re-reading only when a new request starts with exactly the same text. Every request starts with one patient’s own chart, so another patient’s request cannot match it.

The chart is rebuilt when the record store reports a change

The engine checks the record store on every question. When the store reports that part of the record has changed, only that part is fetched again and the chart is condensed again. This takes about a tenth of a second.

Chart size adapts dynamically to the model and turn

The engine imposes no fixed 16k cap: on every turn it measures actual conversation and response overhead against the model’s context window, supports optional Auto sweet-spot calibration informed by long-context evaluations (such as our 16k vs. 32k H200 calibration study ↗), and lets clients pass explicit budget presets (such as 2k to 64k) for controlled testing.

Optional clinical extensions stay modular

Baseline prompt assembly forwards the patient’s question verbatim without ad-hoc rule injection. Specialized research modules, including BM25 note passage search, omitted-record overflow lookup, longitudinal trend summaries, and experimental clinical reconciliation, live behind an opt-in extension boundary so each method can be evaluated independently.

Standalone pilot engine vs. OpenClinAI R&D workbench

Med Agent Hub and the WAHS Explorer Sandbox ↗ form OpenClinAI’s interactive R&D workbench for multi-budget and knowledge-guided experiments, whereas standalone wahs-engine ↗ packages a lean, domain-neutral runtime for the WA Health Summary pilot. Both are evaluated through the Validation Harness.

The model and the front end can be replaced

Both sides of the engine use the standard OpenAI chat format. Pointing it at a different model or server is a configuration change, tested with no code edits. An agency that must use its own approved model can do so.

The pilot runs on the shared UW CIRG H200 GPU server

The GPU server hosts Gemma 4 26B and 12B behind an OpenAI-compatible gateway without downsizing model capability. Concurrent slot allocation and model residency are managed at the GPU server layer rather than inside the engine.

Project status

The standalone engine baseline is designed, integrated, and benchmarked

  • Standalone wahs-engine ↗ combines a pure-standard-library FHIR R4 condensation core with a stateless OpenAI-compatible runtime, keeping optional retrieval and clinical-rule enrichers disabled behind a clean extension boundary.
  • Reads patient records strictly with the caller’s own sign-in token via the fhir-auth security proxy, using version-stamped in-memory caches; patient-facing selective-disclosure privacy policies remain intentionally separated into a dedicated standards-based sharing layer pending team design.
  • Connected across both the WA Health Summary SvelteKit web app (shl-ips ↗) and mobile companion (wahs-mobile-frontend ↗) with clean model tiers (wahs-26b, wahs-12b, wahs-e4b) and dynamic Auto plus 2k to 64k test presets.
  • Benchmarked across two 900-cell H200 studies (16k vs. 32k calibration ↗ and 4-pathway evaluation ↗) plus 384 3-seed portability runs, with published transcripts and scores on reports.openclinai.org ↗.

Glossary

Terms used on this page

FHIR
The standard format health systems use to exchange records. It is detailed and very wordy, which is why records need condensing.
Condensed chart
The short, numbered summary of a patient’s record that the engine builds for the model.
Token, token budget
Models measure text in tokens, each about three-quarters of a word. The token budget is the size limit for the condensed chart.
Safety core
Allergies, active medications, active problems and implants. These are kept first at every chart size.
Citation [N]
A number in the answer that opens the source record it came from.
Knowledge base (KB)
Clinical reference rules an optional extension can attach alongside a question, such as which labs relate to diabetes.
Overflow lookup
An optional extension search of the full record for historical items omitted from a tightly condensed chart.
Note search
Finding the passages in long clinical notes that match the question and adding only those (Okapi BM25 passage retrieval).
KV cache
The model’s short-term memory of text it has just read. A speed feature, and not the knowledge base.
WAHS engine
The middle service this page describes, pairing a pure-standard-library FHIR condensation core with a stateless OpenAI-compatible runtime.
Record store
Where patient records live: a FHIR server behind a gatekeeper (fhir-auth) that returns only the signed-in patient’s records.
Open-weight model
A model whose files can be downloaded and run on servers the team controls.
