Service architecture

Service-to-service flow across WAHS clients, fhir-auth, wahs-engine, and pluggable GPU inference

The target WAHS architecture keeps client frontends lightweight, delegates per-user data access control to WAHS’s existing fhir-auth security proxy, isolates FHIR condensation and clinical reasoning inside a lean standalone wahs-engine middleware service, and speaks standard OpenAI /v1/chat/completions on both sides for plug-and-play model portability.

[1. Client-Agnostic WAHS Frontends & Server-Side BFF] • Unified responsive SvelteKit app (uwcirg/shl-ips) + interoperable mobile-first companion clients • Authenticate via Keycloak OIDC; read/write datasets via fhir-auth and share IPS via shl-server • Browser posts chat turn + optional chart filter to app BFF (/api/chat, Vercel AI SDK) — never straight to GPU │ ▼ Internal network · OpenAI POST /v1/chat/completions (Bearer <keycloak_jwt> + optional wahs.chart_scope) [2. Standalone WAHS Engine Middleware (wahs-engine · Zero Med Agent Hub Dependency)] • Zero HAPI admin credentials: forwards caller's Bearer JWT to fhir-auth (jwt-proxy, meta.security.code == sub) • Bundle Assembler walks masterPatient.link[] → paginated Patient/{datasetId}/$everything (provider imports + My Story/Goals) • Applies optional wahs.chart_scope (source/category/section/IPS filter) + merges unsaved wahs.overlay_resources • Runs wahs_core: 90%–99% condensation (condenser.py) + 4-Layer Clinical KB + ClinicalEntityGraph + Tier-0 lookup • Isolates dataset & KV prefix caches strictly by (verified_sub, datasets_fingerprint, scope_hash) │ ▼ Standard OpenAI POST /v1/chat/completions (LLM_BASE_URL · fixed chart prefix + stream=true) [3. Pluggable OpenAI-Compatible Inference Backend (UW CIRG GPU / Agency Host)] • Default pilot: LiteLLM / Ollama / vLLM on UW CIRG GPU server (Gemma 4 12B default · 26B · E4B) • Zero-code portability: swap approved open-weight models or local agency GPU hosts via config alone • Streams tokens immediately; wahs-engine appends x_wahs ([N] → FHIR UUID/source map + HL7 AI-Provenance)
Zero-Privilege FHIR Assembly

Live star-graph charts, user entries & dynamic scoping

  • Zero service credentials: wahs-engine never connects to raw internal HAPI; forwarding the user’s Keycloak Bearer token through fhir-auth enforces per-user security labels automatically.
  • Provider + patient-authored records: Walking masterPatient.link[] across paginated Patient/$everything bundles pulls both EHR imports and saved patient-authored forms (My Story notes, Goals, Care Needs, POLST) without losing clinical notes stripped by stock HAPI $summary.
  • Flexible chart_scope: Conversations can scope context by data source, category, clinical section, date window, or a specific shared IPS summary, and attach unsaved draft notes via overlay_resources without uploading multi-megabyte bundles from the browser.
Session Isolation & Timeliness

Prefix-cached follow-ups with strict HAPI invalidation

  • Cryptographic tenant boundary: Raw dataset caches key on (verified_sub, dataset_id, lastUpdated), and condensed prompt prefixes key on (verified_sub, datasets_fingerprint, scope_hash)—preventing cross-user or cross-filter bleed.
  • Immediate record timeliness: Whenever a patient imports new EHR records, updates a goal, or deletes a dataset in HAPI, meta.lastUpdated shifts and rebuilds the condensed chart automatically.
  • Deterministic fallback: Placing the [1]...[N] condensed ledger first lets the GPU reuse its KV cache (< 0.3s follow-up prefill), while any cache eviction simply recomputes the identical prompt.
Portability & Lean Packaging

Decoupled clients, swappable models & zero R&D bloat

  • Lean standalone engine vs. R&D workbench: wahs-engine packages pure-Python wahs_core + a thin FastAPI service (~60 MB image, zero OpenMRS/Catalyst dependencies). Med Agent Hub and Validation Harness import wahs_core upstream so benchmarks and production never drift.
  • Frontend independence: Decoupled Keycloak, fhir-auth, shl-server, and wahs-engine services let both the unified SvelteKit web app and mobile-first companion interfaces operate over the exact same patient record.
  • EHIgnite model agnosticism: Standard southbound OpenAI /v1 lets state public-health agencies swap local open-weight models or inference gateways via environment variables while preserving HL7 AI-Provenance transparency.

Worked example: tracing “What are my diabetes labs?” through wahs-engine

To keep follow-up questions fast while reflecting live HAPI FHIR updates, wahs-engine splits every GPU request into two prompt regions: a query-invariant chart prefix at messages[0] and a query-conditioned suffix at messages[-1].

Region 1 · Query-Invariant Prefix (messages[0])

Condensed chart ledger cached across follow-up turns

  • Live assembly (~10 ms check): Calls fhir-auth with the user’s Bearer token, checks MasterPatient + linked Patient.meta.lastUpdated, and re-fetches only newly synced or edited datasets.
  • Deterministic condensation: Compresses the record into the target token budget (default 8k; configurable 1k–32k+), normalizes RxNorm/LOINC/SNOMED labels, numbers entries [1]...[N], and writes [2] Completeness Manifest.
  • Constant prefix: Remains byte-for-byte identical across follow-up questions unless HAPI data changes, chart_scope shifts, or an evaluation explicitly varies the condensation budget.
Region 2 · Query-Conditioned Suffix (messages[-1], ≤ 800 tokens)

Targeted diabetes KB, patient graph & [N] source pills

  • Clinical concept mapping: Injects matched LOINC/ADA rules connecting “diabetes labs” to HbA1c, fasting glucose, eGFR, and urine albumin-creatinine ratio so smaller models do not miss differently named labs.
  • Patient relationship subgraph: Attaches verified edges such as Type 2 diabetes [4] --[MONITORED_BY]--> HbA1c 7.8% [12] plus conditional Tier-0 overflow / Note-RAG excerpts when omitted_clinical_items > 0.
  • Streamed provenance: Sits after prior chat history so messages[0] hits the GPU’s KV cache while x_wahs maps [12] to the exact FHIR Observation UUID and clinic pill.

Session and scope layers across the stack

Separating authentication, chat history, chart freshness, and GPU KV caching eliminates any need for a stateful session database on the GPU server or custom session APIs in WAHS client backends.

State / Session Layer Where It Lives Wire Contract, Ollama KV Connection & Security Guarantee
1. User Auth Identity Keycloak · shl-ips · fhir-auth Authorization: Bearer <keycloak_jwt> travels end-to-end from browser BFF to wahs-engine to fhir-auth; wahs-engine holds zero HAPI admin credentials.
2. Chat Turn History Browser tab RAM (messages[]) Ephemeral conversation array sent over stateless OpenAI /v1/chat/completions. Requires no POST /new-chat-session endpoint and intentionally avoids LiteLLM’s Postgres-backed /v1/responses (previous_response_id) so no PHI prompts or chat transcripts persist on the shared GPU server (store_prompts_in_spend_logs: false).
3. Chart & Prefix Cache wahs-engine in-memory LRU Checks live HAPI meta.lastUpdated via fhir-auth on every turn; reuses (verified_sub, datasets_fingerprint, scope_hash) in < 1 ms when unchanged and re-fetches only modified datasets after EHR imports or patient edits.
4. GPU KV-Cache Slots Ollama / vLLM VRAM Stateless HTTP calls match the unchanged messages[0] token prefix automatically across OLLAMA_NUM_PARALLEL warm VRAM slots—cutting warm 32k follow-ups on UW CIRG H200 MIG 2g.35gb to 2.5s–4.0s median latency with zero session_id and zero cross-patient bleed (slots activate only when the caller already sends matching patient tokens).
Scope Boundary Owner What It Controls & Why It Stays Separate
1. Security & Ownership Scope fhir-auth (jwt-proxy) Hard authorization boundary enforcing meta.security.code == jwt.sub before wahs-engine sees any record.
2. User View Filter wahs.chart_scope + overlay_resources Optional patient-chosen UI lens over their own authorized data (clinic sources, resource categories, date window, specific ips_bundle_id, or unsaved drafts).
3. Token-Budget Priority wahs_core (condenser.py) Deterministic 5-tier clinical priority (1k–32k+ tokens) pinning the HL7 IPS safety core first while logging any trimmed items in [2] Completeness Manifest.
4. Explicit Sharing Posture sharing_posture Separates private patient self-Q&A (patient_self) from explicit external summary/IPS sharing (external_share, 0/288 leaks across 3 seeds).
Inspect OpenAI /v1/chat/completions middleware contract, wahs.chart_scope schema & x_wahs provenance

Server-side routes in WAHS (such as SvelteKit /api/chat/+server.ts using the Vercel AI SDK @ai-sdk/openai-compatible provider) call wahs-engine using standard OpenAI chat completion payloads. Vanilla OpenAI requests with no wahs extension field default automatically to the signed-in user’s full fhir-auth record at the model’s recommended budget; optional wahs.chart_scope and wahs.overlay_resources fields control per-turn filtering and unsaved draft notes, while the final streamed chunk attaches x_wahs citation and HL7 AI Transparency metadata.

Engine internals

Progressive 9-budget condensation, ClinicalEntityGraph, and prompt enrichment

For engineers inspecting the shared wahs_core clinical modules (developed and benchmarked in Med Agent Hub server/fhir/ and packaged without R&D dependencies in standalone wahs-engine), every condensed chart begins with patient demographics at [1] and a machine-readable Completeness Manifest at [2]. When a KB-guided profile executes (such as wahs-12b-kb or wahs-26b-kb), build_wahs_hub_enrichment_block(...) runs conditional Tier-0 overflow recovery, builds a patient-specific ClinicalEntityGraph, and attaches up to 800 tokens of matched clinical guidelines before calling the model.

The engine API accepts a chart size of 512 to 131,072 tokens per request, with a default of 8,192. The 256k row below applies to the Explorer sandbox and the benchmark matrix.

Budget Window Condensation Strategy Omitted Clinical Items Tier-0 Overflow Recovery
256k / 128k Max-window stress-test ceiling expanding multi-decade and ICU charts up to 251,641 extracted clinical tokens. omitted_clinical_items = 0 Skipped (overflow_triggered: false)
64k / 32k / 16k Full longitudinal clinical ledger preserving complete lab timelines, encounters, and decoded UTF-8 clinical notes. omitted_clinical_items = 0 on standard charts Skipped unless massive 7,000-entry export overflows
8k / 4k Recommended Limit sweet spot: preserves active conditions, active medications, allergies, immunizations, and folded lab trajectories. 0 on typical charts; non-zero on multi-decade exports Conditional — runs only when omitted_clinical_items > 0
2k / 1k Strict HL7 IPS Safety Core micro-capsule; older clinical notes and routine historical lab panels overflow the ceiling. omitted_clinical_items > 0 Active — wahs_tools.py recovers question-matched notes and labs with sequential [N] citations
Inspect ClinicalEntityGraph typed relationship edges & orchestration prompt block

wahs_core/clinical_graph.py links seven FHIR resource categories (Condition, MedicationRequest, Observation, DocumentReference, AllergyIntolerance, Immunization, and Organization) across five typed clinical edges while preserving original [N] citation numbers so 4B–12B models do not have to infer multi-hop cardiorenal or anticoagulation hazards from raw text alone. Paired wahs-*-raw profiles omit this block for zero-hint baseline ablations.

Graph Edge Type Source → Target Nodes Clinical Logic & Knowledge Base Grounding
TREATS MedicationRequest → Condition Maps active medications to documented clinical indications via RxNorm class lookup and AHA/ACC/ADA/KDIGO mappings (e.g., Apixaban [6] --[TREATS]--> Atrial fibrillation [5]).
CONTRAINDICATED_OR_DOSE_ADJUST_IN MedicationRequest → Condition / Observation / AllergyIntolerance Flags renal dosing thresholds, hyperkalemia hazards, supratherapeutic INR, NSAID nephrotoxicity/bleeding, and allergy cross-reactivity (e.g., Spironolactone [7] --[CONTRAINDICATED_OR_DOSE_ADJUST_IN]--> Potassium 5.6 mEq/L [10]).
MONITORED_BY Condition / MedicationRequest → Observation Connects chronic diseases and high-alert therapies to their longitudinal LOINC laboratory and vital trajectories (eGFR, Creatinine, Potassium, HbA1c, INR, NT-proBNP, LDL-C, TSH).
CONTRADICTED_OR_MODIFIED_BY_NOTE Condition (Active ↔ Resolved) Detects structured cross-organization discrepancies where the same condition is marked active at one clinic and resolved at another, while full narrative notes route through Note-RAG / Tier-0 overflow.
REPORTED_BY_ORG Clinical Node → Organization Preserves multi-facility care provenance (e.g., primary health system vs. outside urgent care or external reference laboratory).
