Service architecture

Service-to-service flow across WAHS clients, fhir-auth, wahs-engine, and pluggable GPU inference

The target WAHS architecture keeps client frontends lightweight, delegates per-user data access control to WAHS’s existing fhir-auth security proxy, isolates FHIR condensation and clinical reasoning inside a lean standalone wahs-engine middleware service, and speaks standard OpenAI /v1/chat/completions on both sides for plug-and-play model portability.

[1. Client-Agnostic WAHS Frontends & Server-Side BFF] • Responsive SvelteKit web app + interoperable mobile-first companion client • Authenticate via Keycloak OIDC; read/write datasets via fhir-auth and share IPS via shl-server • Browser posts chat turn + optional chart filter to app BFF (/api/chat), never straight to GPU │ ▼ Internal network · OpenAI POST /v1/chat/completions (Bearer access token + optional chart_scope) [2. Standalone WAHS Engine Middleware (wahs-engine)] • Zero HAPI admin credentials: forwards caller's Bearer JWT to fhir-auth (per-user security proxy) • Fetches linked patient datasets (provider imports + personal My Story / Goals entries) • Applies optional chart_scope (source/category/section/IPS filter) + merges unsaved drafts • Continuous 3-tier verbatim-first condensation (Tier 0 verbatim when it fits, Tier 1 uniform RLE, Tier 2 safety-core packing) • Optional research extension shelf (disabled in baseline): BM25 note search, overflow lookup, trend math, reconciliation • Isolates dataset and prefix caches strictly per user identity and record scope │ ▼ Standard OpenAI POST /v1/chat/completions (fixed chart prefix + stream=true) [3. Pluggable OpenAI-Compatible Inference Backend (UW CIRG GPU / Agency Host)] • Model aliases: wahs-26b (default), wahs-12b, wahs-e4b on UW CIRG H200 or local inference servers • Zero-code portability: swap approved open-weight models or local agency GPU hosts via configuration • Streams tokens immediately; engine attaches x_wahs ([N] → FHIR UUID/source map + HL7 AI-Provenance)
Engine scope & explicit non-goals: wahs-engine owns stateless per-turn FHIR bundle assembly via fhir-auth, domain-neutral 3-tier verbatim-first condensation, dynamic per-turn context sizing, optional research extension hooks, and OpenAI /v1/chat/completions + x_wahs provenance mapping. It intentionally does not own OIDC login UI, persistent chat databases, HAPI admin credentials, SMART Health Link issuance, patient-facing selective-disclosure privacy policies (kept decoupled for standards-based sharing design), GPU VRAM scheduling, or evaluation judging.
Zero-Privilege FHIR Assembly

Live star-graph charts, user entries & dynamic scoping

  • Zero service credentials: wahs-engine never connects to raw internal HAPI; forwarding the user’s Keycloak Bearer token through fhir-auth ↗ enforces per-user security labels automatically.
  • Provider + patient-authored records: Traversing linked patient datasets across paginated Patient/$everything bundles pulls both EHR imports and saved patient-authored forms (My Story notes, Goals, Care Needs, POLST) without losing clinical notes stripped by stock IPS summaries.
  • Flexible scoping: Conversations can filter context by clinic source, resource category, clinical section, date window, or a specific shared IPS summary, and attach unsaved draft notes without uploading multi-megabyte bundles from the browser.
Session Isolation & Timeliness

Prefix-cached follow-ups with strict freshness invalidation

  • Tenant boundary: Raw dataset and condensed prefix caches partition strictly by verified user identity, active dataset versions, and scope hash, preventing cross-user or cross-filter bleed.
  • Immediate record timeliness: Whenever a patient imports new EHR records, updates a goal, or deletes a dataset in HAPI, meta.lastUpdated shifts and rebuilds the condensed chart automatically.
  • Deterministic fallback: Placing the [1]...[N] condensed ledger first lets the GPU reuse its KV cache (< 0.3s follow-up prefill), while any cache eviction simply recomputes the identical prompt.
Portability & Lean Packaging

Decoupled clients, swappable models & R&D parity

  • Lean runtime vs. R&D workbench: wahs-engine packages a pure-standard-library FHIR condensation core and thin OpenAI-compatible runtime with zero EHR or SQL workbench dependencies, while Med Agent Hub and Validation Harness benchmark the same condensation principles.
  • Frontend independence: Decoupled Keycloak, fhir-auth, SMART Health Links, and wahs-engine services let both the unified SvelteKit web app and mobile companion operate over the same patient record.
  • Model agnosticism: Standard southbound OpenAI /v1 APIs let state public-health agencies swap local open-weight models or approved inference gateways via configuration while preserving HL7 AI-Provenance ↗.

Worked example: tracing “What are my diabetes labs?” through wahs-engine

To keep follow-up questions fast while reflecting live FHIR updates, wahs-engine splits every GPU request into two prompt regions: a query-invariant chart prefix first and a turn-local suffix at the end.

Region 1 · Query-Invariant Prefix

Condensed chart ledger cached across follow-up turns

  • Live assembly (~10 ms check): Calls fhir-auth with the user’s Bearer token, checks linked patient meta.lastUpdated stamps, and re-fetches only newly synced or edited datasets.
  • Deterministic condensation: Keeps everything verbatim whenever it fits available turn tokens (Tier 0 verbatim when unbounded or within window; Tier 1 uniform series folding and Tier 2 safety-core packing + continuous note water-filling only when constrained), normalizes dates cleanly without mutating clinical meaning, numbers entries [1]...[N], and writes [2] Completeness Manifest.
  • Constant prefix: Remains byte-for-byte identical across follow-up questions unless HAPI data changes, chart_scope shifts, or an evaluation varies the condensation budget.
Region 2 · Turn Suffix & Optional Extensions

Verbatim question forwarding + opt-in research shelf

  • Clean pass-through by default: In the standard baseline configuration, the turn suffix forwards the caller’s exact question verbatim with zero hidden prompt mutations or multi-step tool loops.
  • Modular extension interface: When an operator or benchmark enables research extensions (BM25 note passage search, overflow lookup, longitudinal trend summaries, or clinical reconciliation), bounded evidence attaches cleanly with extension provenance recorded under x_wahs.
  • Streamed provenance: Placing the changing question after conversation history lets the GPU hit its cached chart prefix while x_wahs maps inline [N] citations to FHIR resource UUIDs and clinics.

Session and scope layers across the stack

Separating authentication, chat history, chart freshness, and GPU KV caching eliminates any need for a stateful session database on the GPU server or custom session APIs in WAHS client backends.

State / Session Layer Where It Lives Wire Contract, Prefix Caching & Security Guarantee
1. User Auth Identity Keycloak · Web App · fhir-auth Authorization: Bearer <jwt> travels end-to-end from browser BFF to wahs-engine to fhir-auth; wahs-engine holds zero HAPI admin credentials and supports optional local RS256 JWKS signature, issuer, and audience verification.
2. Chat Turn History Browser tab memory Ephemeral conversation array sent over stateless OpenAI /v1/chat/completions. Uses no server session database and disables prompt retention on inference gateways so clinical transcripts never persist on shared GPU hosts.
3. Chart & Prefix Cache wahs-engine memory LRU Checks live FHIR meta.lastUpdated stamps via fhir-auth on every turn; reuses cached per-user condensed prefixes in < 1 ms under entry-count and memory caps when unchanged, and re-fetches only modified datasets after EHR imports or patient edits.
4. GPU KV-Cache Slots Inference server VRAM Stateless HTTP calls match identical leading chart prefixes automatically across concurrent VRAM slots on UW CIRG H200 GPUs, reducing warm follow-up latency to 2.5s–4.0s without session IDs and with zero risk of cross-patient leakage.
Scope Boundary Owner What It Controls & Why It Stays Separate
1. Security & Ownership Scope fhir-auth proxy Hard authorization boundary enforcing per-subject record ownership before wahs-engine sees any clinical resource.
2. User View Filter Client chart_scope Optional patient-chosen UI lens over their own authorized data (clinic sources, categories, date window, specific IPS bundle, or unsaved drafts).
3. Dynamic Token-Budget Sizing Per-turn window resolver No hardcoded chart token cap: resolves available capacity dynamically from the model’s context window minus exact turn and output tokens (plus optional Auto sweet-spot calibration and explicit caller budget overrides), logging any omissions in [2] Completeness Manifest.
4. Selective Disclosure Privacy Dedicated Sharing Layer Decoupled from the core condensation runtime so patient-facing privacy redaction follows HL7 FHIR DS4P ↗ and explicit consent workflows rather than implicit lexical rules.

Engine internals

Continuous 3-tier condensation and modular research extensions

wahs-engine strictly separates condensation mechanism (domain-neutral FHIR R4 extraction, SHA-256 note deduplication, and continuous 3-tier verbatim-first condensation in a pure-standard-library core) from per-turn sizing policy (measuring actual conversation and response tokens against the active model’s context window on each turn). Optional research extensions (BM25 note search, omitted-record overflow lookup, longitudinal trend math, and clinical reconciliation) sit behind a clean extension interface and remain disabled in the baseline path. Meanwhile, Med Agent Hub powers the interactive WAHS Explorer Sandbox ↗ for multi-budget and knowledge-guided experimentation.

Because condensation carries no hardcoded 16k limit or per-section item quotas, small and mid-sized records stay 100% verbatim while massive multi-year exports shrink smoothly only to fit exact turn capacity or an explicit caller budget preset (such as 2k through 64k). Research into long-context degradation is informed by Liu et al., Lost in the Middle (TACL, 2024) ↗ and our 16k vs. 32k H200 calibration study ↗.

Condensation Tier When It Activates How Context Is Prepared Completeness Guarantee
Tier 0 · Verbatim Full Record Chart fits available turn capacity (or budget is unbounded) Strips FHIR JSON syntax overhead and duplicate clinical notes via SHA-256 hashing; emits every clinical resource and decoded note verbatim. Zero omitted items; 100% intact narratives and timestamps.
Tier 1 · Uniform Series Folding Verbatim record exceeds available turn capacity Uniformly folds repeated identical historical series strictly by FHIR code and unit without static keep-quotas or clinical mutation heuristics. Zero lost safety-core items; folded series retain earliest, peak, and latest values.
Tier 2 · Safety Core & Water-Filled Notes Folded chart still exceeds available turn capacity Reserves the HL7 IPS safety core ↗ (allergies, active meds, active problems, implants), packs remaining items by recency, and dynamically water-fills clinical notes across all remaining tokens. Logs exact per-section omissions in [2] Completeness Manifest for grounded citation ↗ and abstention.
Inspect modular research extensions & typed clinical reconciliation relationships

Disabled in the clean baseline runtime, four optional research modules can be enabled selectively for comparative evaluation or explored in the WAHS Explorer Sandbox ↗: Note Passage Search (Okapi BM25 over long clinical narratives), Overflow Lookup (recovering question-relevant omitted records with sequential [N] links), Longitudinal Trend Summaries, and Experimental Clinical Reconciliation. When active, clinical reconciliation builds typed cross-clinic links over seven FHIR resource categories so smaller models (4B–26B) do not have to infer multi-hop hazards from flat text alone (evaluated in the 4-Pathway H200 Benchmark ↗):

Relationship Type Source → Target Resources Clinical Standard / Evidence Rationale
CROSS_REACTS_WITH MedicationRequest → AllergyIntolerance Flags documented drug allergies and cross-reactive therapeutic classes against active prescriptions.
CONTRAINDICATED_OR_DOSE_ADJUST_IN MedicationRequest → Condition / Observation Surfaces KDIGO renal dosing ↗, hyperkalemia, supratherapeutic INR, NSAID bleeding, and hypoglycemia thresholds.
CONFLICTS_WITH MedicationRequest ↔ MedicationRequest · Condition ↔ Condition · Immunization ↔ Immunization Surfaces brand-versus-generic and therapeutic-class duplicates via NLM RxNorm ↗, conflicting disease stages, and CDC ACIP ↗ anomalies.
CONTRADICTED_OR_MODIFIED_BY_NOTE MedicationRequest / Condition → DocumentReference / Condition Detects cross-clinic active-versus-resolved discrepancies and hospital discharge notes instructing a patient to hold an active outpatient medication (HL7 CIRI ↗).
MONITORED_BY Condition / MedicationRequest → Observation Connects chronic diseases and high-alert therapies to unit-consistent LOINC ↗ lab trajectories (eGFR, Creatinine, Potassium, HbA1c, INR, NT-proBNP).
TREATS MedicationRequest → Condition Maps active medications to documented clinical indications via RxNorm and guideline mappings.
REPORTED_BY_ORG Clinical Node → Organization Preserves multi-facility care provenance across health systems, urgent care clinics, and outside laboratories.
