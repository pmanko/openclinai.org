Service architecture

Service-to-service flow across WAHS clients, fhir-auth, wahs-engine, and pluggable GPU inference

The target WAHS architecture keeps client frontends lightweight, delegates per-user data access control to WAHS’s existing fhir-auth security proxy, isolates FHIR condensation and clinical reasoning inside a lean standalone wahs-engine middleware service, and speaks standard OpenAI /v1/chat/completions on both sides for plug-and-play model portability.

[1. Client-Agnostic WAHS Frontends & Server-Side BFF] • Unified responsive SvelteKit app (uwcirg/shl-ips) + interoperable mobile-first companion clients • Authenticate via Keycloak OIDC; read/write datasets via fhir-auth and share IPS via shl-server • Browser posts chat turn + optional chart filter to app BFF (/api/chat, Vercel AI SDK), never straight to GPU │ ▼ Internal network · OpenAI POST /v1/chat/completions (Bearer <keycloak_jwt> + optional wahs.chart_scope) [2. Standalone WAHS Engine Middleware (wahs-engine · Zero Med Agent Hub Dependency)] • Zero HAPI admin credentials: forwards caller's Bearer JWT to fhir-auth (jwt-proxy, meta.security.code == sub) • Bundle Assembler walks masterPatient.link[] → paginated Patient/{datasetId}/$everything (provider imports + My Story/Goals) • Applies optional wahs.chart_scope (source/category/section/IPS filter) + merges unsaved wahs.overlay_resources • Runs wahs_core: 3-tier verbatim-first condensation (Tier 0 verbatim when <= available tokens, Tier 1 uniform RLE, Tier 2 water-filled) • Optional wahs_extensions/ shelf (unplugged by default when WAHS_ENABLED_ENRICHERS=""): note_rag, overflow_lookup, temporal_trends • Isolates dataset & KV prefix caches strictly by (verified_sub, datasets_fingerprint, scope_hash) │ ▼ Standard OpenAI POST /v1/chat/completions (LLM_BASE_URL · fixed chart prefix + stream=true) [3. Pluggable OpenAI-Compatible Inference Backend (UW CIRG GPU / Agency Host)] • Clean production model aliases: wahs-26b (default), wahs-12b, wahs-e4b (Ollama/LiteLLM on UW CIRG H200 or llama-router) • Zero-code portability: swap approved open-weight models or local agency GPU hosts via config alone • Streams tokens immediately; wahs-engine appends x_wahs ([N] → FHIR UUID/source map + HL7 AI-Provenance)
Engine scope & explicit non-goals: wahs-engine owns only stateless per-turn FHIR bundle assembly via fhir-auth (with optional local RS256 JWKS defense-in-depth), domain-neutral wahs_core 3-tier condensation, optional operator-configured wahs_extensions plugins, exact offline token sizing, and OpenAI /v1/chat/completions + x_wahs provenance mapping. It intentionally does not own OIDC login UI, persistent chat databases, HAPI admin credentials, SMART Health Link issuance (shl-server), unbuilt patient-facing selective-disclosure privacy policies (W9 deferred pending team design), GPU VRAM scheduling, or LLM-as-a-judge evaluation scoring.
Zero-Privilege FHIR Assembly

Live star-graph charts, user entries & dynamic scoping

  • Zero service credentials: wahs-engine never connects to raw internal HAPI; forwarding the user’s Keycloak Bearer token through fhir-auth enforces per-user security labels automatically.
  • Provider + patient-authored records: Walking masterPatient.link[] across paginated Patient/$everything bundles pulls both EHR imports and saved patient-authored forms (My Story notes, Goals, Care Needs, POLST) without losing clinical notes stripped by stock HAPI $summary.
  • Flexible chart_scope: Conversations can scope context by data source, category, clinical section, date window, or a specific shared IPS summary, and attach unsaved draft notes via overlay_resources without uploading multi-megabyte bundles from the browser.
Session Isolation & Timeliness

Prefix-cached follow-ups with strict HAPI invalidation

  • Cryptographic tenant boundary: Raw dataset caches key on (verified_sub, dataset_id, lastUpdated), and condensed prompt prefixes key on (verified_sub, datasets_fingerprint, scope_hash), preventing cross-user or cross-filter bleed.
  • Immediate record timeliness: Whenever a patient imports new EHR records, updates a goal, or deletes a dataset in HAPI, meta.lastUpdated shifts and rebuilds the condensed chart automatically.
  • Deterministic fallback: Placing the [1]...[N] condensed ledger first lets the GPU reuse its KV cache (< 0.3s follow-up prefill), while any cache eviction simply recomputes the identical prompt.
Portability & Lean Packaging

Decoupled clients, swappable models & zero R&D bloat

  • Lean standalone engine vs. R&D workbench: wahs-engine packages pure-Python wahs_core + a thin FastAPI service (~60 MB image, zero OpenMRS/Catalyst dependencies). Med Agent Hub and Validation Harness import wahs_core upstream so benchmarks and production never drift.
  • Frontend independence: Decoupled Keycloak, fhir-auth, shl-server, and wahs-engine services let both the unified SvelteKit web app and mobile-first companion interfaces operate over the exact same patient record.
  • EHIgnite model agnosticism: Standard southbound OpenAI /v1 lets state public-health agencies swap local open-weight models or inference gateways via environment variables while preserving HL7 AI-Provenance transparency.

Worked example: tracing “What are my diabetes labs?” through wahs-engine

To keep follow-up questions fast while reflecting live HAPI FHIR updates, wahs-engine splits every GPU request into two prompt regions: a query-invariant chart prefix at messages[0] and a query-conditioned suffix at messages[-1].

Region 1 · Query-Invariant Prefix (messages[0])

Condensed chart ledger cached across follow-up turns

  • Live assembly (~10 ms check): Calls fhir-auth with the user’s Bearer token, checks MasterPatient + linked Patient.meta.lastUpdated, and re-fetches only newly synced or edited datasets.
  • Deterministic condensation: Keeps everything verbatim unless a chart exceeds available tokens (Tier 0 verbatim when target_tokens is unset or fits; Tier 1 uniform ontology-free RLE folding and Tier 2 monotonic packed + water-filled notes only when constrained), normalizes dates cleanly without heuristic clinical mutations, numbers entries [1]...[N], and writes [2] Completeness Manifest.
  • Constant prefix: Remains byte-for-byte identical across follow-up questions unless HAPI data changes, chart_scope shifts, or an evaluation explicitly varies the condensation budget.
Region 2 · Turn Suffix & Optional Enrichers (messages[-1])

Clean user question + opt-in wahs_extensions/

  • Zero-mutation pass-through by default: When WAHS_ENABLED_ENRICHERS="", messages[-1] forwards the caller's exact question verbatim without importing wahs_extensions or running LLM tool loops.
  • Opt-in enricher shelf: When operators explicitly enable modules via WAHS_ENABLED_ENRICHERS (note_rag, overflow_lookup, temporal_trends, experimental.clinical_reconciliation), bounded blocks and disclosures attach cleanly inside x_wahs.enrichers.
  • Streamed provenance: Sits after prior chat history so messages[0] hits the GPU’s KV cache while x_wahs maps [N] citations to exact FHIR resource UUIDs and clinics.

Session and scope layers across the stack

Separating authentication, chat history, chart freshness, and GPU KV caching eliminates any need for a stateful session database on the GPU server or custom session APIs in WAHS client backends.

State / Session Layer Where It Lives Wire Contract, Ollama KV Connection & Security Guarantee
1. User Auth Identity Keycloak · shl-ips · fhir-auth Authorization: Bearer <keycloak_jwt> travels end-to-end from browser BFF to wahs-engine to fhir-auth; wahs-engine holds zero HAPI admin credentials and supports optional local RS256 JWKS signature, iss, and aud verification (WAHS_JWT_JWKS_URL).
2. Chat Turn History Browser tab RAM (messages[]) Ephemeral conversation array sent over stateless OpenAI /v1/chat/completions. Requires no POST /new-chat-session endpoint and intentionally avoids LiteLLM’s Postgres-backed /v1/responses (previous_response_id) so no PHI prompts or chat transcripts persist on the shared GPU server (store_prompts_in_spend_logs: false).
3. Chart & Prefix Cache wahs-engine byte-bounded LRU Checks live HAPI meta.lastUpdated via fhir-auth on every turn; reuses (verified_sub, datasets_fingerprint, scope_hash) in < 1 ms under entry-count and byte-size caps when unchanged, and re-fetches only modified datasets after EHR imports or patient edits.
4. GPU KV-Cache Slots Ollama / vLLM VRAM Stateless HTTP calls match the unchanged messages[0] token prefix automatically across OLLAMA_NUM_PARALLEL warm VRAM slots, cutting warm 32k follow-ups on UW CIRG H200 MIG 2g.35gb to 2.5s–4.0s median latency with zero session_id and zero cross-patient bleed (slots activate only when the caller already sends matching patient tokens).
Scope Boundary Owner What It Controls & Why It Stays Separate
1. Security & Ownership Scope fhir-auth (jwt-proxy) Hard authorization boundary enforcing meta.security.code == jwt.sub before wahs-engine sees any record.
2. User View Filter wahs.chart_scope + overlay_resources Optional patient-chosen UI lens over their own authorized data (clinic sources, resource categories, date window, specific ips_bundle_id, or unsaved drafts).
3. Token-Budget Priority wahs_core & per-turn budget resolver Zero static token ceilings in core: resolves available capacity dynamically from context_window - exact_turn_overhead (with optional per-model WAHS_PREFERRED_CHART_TOKENS in Auto mode and un-clamped target_budget_tokens overrides), uniformly folds repeated series only over budget, water-fills notes dynamically, and logs omitted items in [2] Completeness Manifest.
4. Patient Privacy / Selective Disclosure Unbuilt (Deferred Pending Team Design) No premature regex redaction or sharing_posture runs in core extraction/runtime; future DS4P/SD-JWT selective disclosure belongs in a dedicated, explicitly consented privacy layer.
Inspect OpenAI /v1/chat/completions middleware contract, wahs.chart_scope schema & x_wahs provenance

Server-side routes in WAHS (such as SvelteKit /api/chat/+server.ts) call wahs-engine using clean model aliases (wahs-26b default, wahs-12b, wahs-e4b) and standard OpenAI chat completion payloads (plus POST /v1/wahs/context/preview for pre-chat inspection). Prompt sizing and upstream stream connection are validated before committing HTTP 200 SSE headers, and vanilla OpenAI SDK callers can pass wahs.emit_stream_events: false to suppress x_wahs_stream sideband chunks.

Engine internals

3-tier verbatim-first condensation (`wahs_core`) and opt-in `wahs_extensions/` shelf

Inside standalone wahs-engine, wahs_core (100% Python stdlib verified via python -S) implements pure structural FHIR R4 extraction, SHA-256 note deduplication, and continuous 3-tier verbatim-first condensation: Tier 0 keeps the complete record and notes verbatim whenever target_tokens is unset or fits available window capacity; Tier 1 uniformly run-length folds repeated historical series strictly by FHIR code/unit; Tier 2 preserves the mandatory IPS safety core, packs monotonic recency items, and dynamically water-fills included clinical notes across remaining capacity (zero hardcoded 400-char caps or section quotas). Reusable enrichment modules (note_rag, overflow_lookup, temporal_trends, and experimental.clinical_reconciliation) live cleanly isolated in src/wahs_extensions/ behind wahs_core.ports.ContextEnricher and are unplugged by default (WAHS_ENABLED_ENRICHERS=""). Upstream Med Agent Hub pins the earlier R&D snapshot (85fb799) cleanly so experimental evaluations remain decoupled.

The engine computes physical chart capacity dynamically per request from the model’s context_window minus exact non-chart turn and output tokens (no hardcoded 16k cap). Operators can configure optional per-model preferred_chart_tokens for Auto sweet-spot tuning (informed by our historical H200 16k vs. 32k calibration), while callers and UI budget levers can request any positive target_budget_tokens up to physical window capacity. The 256k row below applies to the Explorer sandbox and benchmark matrices.

Inspect ClinicalEntityGraph typed relationship edges & orchestration prompt block

wahs_core/clinical_graph.py links seven FHIR resource categories (Condition, MedicationRequest, Observation, DocumentReference, AllergyIntolerance, Immunization, and Organization) across seven typed clinical edges while preserving original [N] citation numbers so 4B to 26B models do not have to infer multi-hop cardiorenal, allergy, or anticoagulation hazards from raw text alone. Paired wahs-*-chart profiles omit this block for zero-hint baseline ablations.

Graph Edge Type Source → Target Nodes Clinical Logic & Knowledge Base Grounding
CROSS_REACTS_WITH MedicationRequest → AllergyIntolerance Flags documented drug allergies and beta-lactam/sulfonamide/NSAID class cross-reactivity against active prescriptions before generation.
CONTRAINDICATED_OR_DOSE_ADJUST_IN MedicationRequest → Condition / Observation Flags renal dosing thresholds, hyperkalemia hazards (including potassium salts), supratherapeutic INR, NSAID nephrotoxicity/bleeding, and directional low-HbA1c/glucose hypoglycemia risks (e.g., Spironolactone [7] --[CONTRAINDICATED_OR_DOSE_ADJUST_IN]--> Potassium 5.6 mEq/L [10]).
CONFLICTS_WITH MedicationRequest ↔ MedicationRequest · Condition ↔ Condition · Immunization ↔ Immunization Surfaces brand-versus-generic and same-class duplicate therapies, mutually exclusive CKD or NYHA heart-failure stages, and CDC ACIP vaccine interval anomalies across clinics.
CONTRADICTED_OR_MODIFIED_BY_NOTE MedicationRequest / Condition → DocumentReference / Condition Detects cross-clinic active-versus-resolved condition discrepancies and hospital or walk-in clinical notes instructing a patient to hold or stop an outpatient medication (unless superseded by a later resume note).
MONITORED_BY Condition / MedicationRequest → Observation Connects chronic diseases and high-alert therapies to unit-separated longitudinal LOINC laboratory and vital trajectories (eGFR, Creatinine, Potassium, HbA1c, INR, NT-proBNP, LDL-C, TSH).
TREATS MedicationRequest → Condition Maps active medications to documented clinical indications via RxNorm class lookup and AHA/ACC/ADA/KDIGO mappings (e.g., Apixaban [6] --[TREATS]--> Atrial fibrillation [5]).
REPORTED_BY_ORG Clinical Node → Organization Preserves multi-facility care provenance (e.g., primary health system vs. outside urgent care or external reference laboratory).
