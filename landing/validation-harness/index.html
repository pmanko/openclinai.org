Validation Harness

Repeatable clinical AI experiments.

Run configured experiments against clinical AI applications as clinicians use them inside OpenMRS and OpenELIS, capture stage-by-stage streaming telemetry and source evidence, evaluate clinical accuracy and citation grounding, and size deployment hardware under realistic multi-user clinic concurrency.

Inspect published evidence → Read setup and documentation →

How the updated validation approach works

01

Measure the real OpenMRS stream

Drive /ws/rest/v1/chartsearchai/chat/stream under provisioned clinical roles and locations. Timestamp every Server-Sent Event frame as it arrives so Time to First Token (TTFT), initial answer completion (answer_done), and background review or In-Depth completion (turn_done) are measured separately rather than collapsed into one wall-clock number.

02

Separate capability from sampler artifacts

Use an HTTP wire tap (engine-tap) between OpenMRS and the model server to record exact prompt payloads, token counts and prompt-cache hits, and to test both shared-engine parity and out-of-the-box LocalLlmEngine sampler rules (such as conditional DRY repetition penalties on long charts).

03

Stress-test multi-clinician concurrency

Run N=1, 2, 4+ simultaneous clinical sessions across distinct OpenMRS accounts (eval-doctor, eval-nurse, eval-pharmacy, eval-clerk) so concurrent turns do not preempt one another’s conversation or share a single user’s rate-limit bucket. Report Service-Level Objective (SLO) goodput alongside p50/p95 latency.

What each run records: quality, grounding and streaming telemetry

Evaluating a clinical chart assistant requires both clinical correctness (whether the answer is faithful to the patient’s longitudinal record and safe for clinical review) and interactive responsiveness (how quickly a clinician sees the first token and the completed main answer). The harness records both layers in each run bundle.

Hardware and deployment sizing for OpenMRS decision makers

When ChartSearchAI runs with fullChart enabled on a longitudinal HIV patient record, each question sends roughly 12,200 input tokens of clinical history. Deployment sizing is therefore governed by prompt prefill compute (TTFT) and KV-cache memory per concurrent clinician slot. Shared benchmarks and open-source tooling we build on

Rather than reinventing evaluation metrics or load-testing primitives from scratch, the Validation Harness adopts conventions from active clinical NLP benchmarks and open-source LLM serving tools:

Benchmark / toolFocus areaHow OpenClinAI uses or adapts its ideas
ArchEHR-QA & EHRNoteQA (PhysioNet / BioNLP)Patient-specific multi-note EHR question answering and sentence-level evidence groundingSeparates evidence identification (whether the assistant retrieved and cited the right OpenMRS chart records in score-citations) from answer-evidence alignment (whether each clinical claim is supported by its cited record in sources.v1).
HealthBench (OpenAI) & MedHELM (Stanford CRFM)Multi-turn clinical conversations, physician-authored rubrics and LLM-jury evaluationCombines scenario-specific deterministic turn checks (expectations.py) with multi-axis rubric grading and explicit clinical harm flags, anchored to human clinician reviews via Prediction-Powered Inference (PPI).
NVIDIA AIPerf, GuideLLM & vllm bench serveStreaming LLM serving telemetry (TTFT, ITL, TPOT), multi-turn prefix caching and SLO goodputAdopts streaming milestone decomposition, turn-position prefix-cache tracking (turn_1_ttft_p50_ms vs. turn_2plus_ttft_p50_ms, cache_hit_ratio) and SLO goodput in harness-cli validate concurrency, while keeping OpenMRS authentication, session isolation and QueryStore retrieval in the loop.
